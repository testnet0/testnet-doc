# Task Execution Monitoring & Result Parsing

When a workflow dispatches atomic `Task` envelopes to remote Go scanning nodes, security engineers can monitor execution via **Task Detail Views**, **ANSI Real-Time Terminal Logs (`LogViewer`)**, and TestNet's **7 Structured Output Parsing Pipelines (`OutputParser`)**.

---

## 1. Task Lifecycle & Health Monitoring

Click **"Detail"** on any row inside **"Task Management" -> "Task List"** to inspect underlying probe telemetry:

### State Machine Transitions (`TaskStateMachine`)
The task execution engine enforces strict state machine rules to guarantee idempotency and reliability across distributed nodes:
- ⏳ **PENDING**: The task generated by workflow compilation is queued, waiting for an online Go scanning node.
- 📌 **ASSIGNED**: The task envelope has been picked up by a specific scanning probe (via HTTP long polling or WebSocket).
- 🔄 **RUNNING**: The node has launched the Docker container or local process and is streaming stdout/stderr logs.
- ✅ **COMPLETED**: The process exited with code `0`, and outputs were parsed into asset entities by `OutputParser`.
- ❌ **FAILED**: The command returned a non-zero exit code, hit resource limits, timed out, or encountered parsing exceptions.
- ⏭️ **SKIPPED**: Automatically skipped due to empty upstream inputs or a `false` Aviator condition expression (`condition`).

### Heartbeats, Circuit Breaking & Auto-Retries
- **Probe Heartbeat Tracking**: The backend continuously tracks probe liveliness. If a node loses connectivity or crashes mid-execution past the heartbeat threshold, TestNet automatically triggers circuit breaking.
- **Automated Retries**: If the parent workflow specifies `maxRetries` (e.g. `2`), transient network timeouts or failures automatically revert the task state to `PENDING` for re-dispatch.

### Manual Interventions & Lifecycle Control
- **Force Kill**: For runaway or stalled `RUNNING` tasks, administrators can click **"Kill"**. The server sends an immediate termination signal to the probe, tearing down target Docker containers.
- **Single Task Retry**: Click **"Retry"** on any `FAILED` task row to re-trigger execution on an active node without re-running the entire workflow.

## 2. Real-Time ANSI Colored Terminal Logs (`LogViewer`)

Without SSH access to remote probe nodes, TestNet's **Real-Time Log Viewer (`LogViewer`)** gives you a fluid terminal-grade monitoring experience right from the console:

### Real-Time Streaming Architecture
- Remote scanning probes capture `stdout` and `stderr` buffers in real time, pushing them over secure streaming channels;
- The backend relays these streams with ultra-low latency directly to your web console.

### Colored Styling & Search Filtering
- Native terminal color codes (red for critical alerts, yellow for warnings, green for info) render perfectly as styled text;
- **Live Search & Filter**: Type keywords into the search bar or toggle log-level buttons to jump instantly to error stack traces across thousands of output lines.

## 3. The 7 Output Parsing Pipelines

Because third-party security utilities produce wildly different output formats (JSON lines, raw text tables, XML, CSV), TestNet implements **7 robust structured parsing engines** to convert raw scanner logs directly into structured asset entries:

| Parsing Engine | Identifier | Target Tools & Format Characteristics | Core Mechanism |
| :--- | :--- | :--- | :--- |
| **JSON Parser** | `JSON` | Complete JSON object or array payload | Deserializes JSON directly and maps fields onto asset properties |
| **JSON Lines Parser** | `JSONL` | One independent JSON object per line (e.g., `subfinder`, `httpx`, `nuclei`) | Streaming line-by-line ingestion with minimal RAM overhead, ideal for parsing 100k+ concurrent results |
| **CSV Table Parser** | `CSV` | Comma or tab-separated data tables | Maps column header strings directly onto asset entity fields |
| **Regex Parser** | `REGEX` | Unstructured plaintext stdout (e.g., raw `nmap` text logs, `banner` captures) | Uses named regex capture groups to extract IPs, ports, versions, and CVE identifiers |
| **XML Document Parser** | `XML` | Traditional scanner files (`Nmap XML`, `Nessus XML`) | Navigates XML hierarchies to accurately extract complex vulnerability proof blocks and asset details |
| **Line Text Parser** | `LINE` | Simple plaintext lists (subdomains, IP lists, directory brute-force paths) | Trims each line into a standalone entity field value |
| **Pipeline Chain** | `PIPELINE` | Complex multi-stage output streams | Chains multiple engines sequentially (e.g., regex extraction first, followed by JSONL parsing on captured blocks) |

> [!NOTE]
> Parsed outputs are automatically routed and saved: discovered hosts and ports are immediately saved into the **Asset Graph**, while confirmed vulnerability findings (`PoC`) generate **Vulnerability Records** and trigger instant alerts via the Notification module.
